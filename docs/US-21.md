# US-21 · Automação ampliada da verificação (CI)

Épico E6 (Qualidade e entrega). Branch: `feat/us-21-ci`, criada sobre `feat/us-20-verificacao`.

> **Critérios inferidos.** O catálogo não estava disponível. No planejamento, a US-21 é a "automação ampliada", o
> primeiro corte em caso de falta de capacidade. Aqui ela automatiza a verificação da US-20 no GitHub Actions.
> Confirme com o PO.

## Critérios (hipótese)

| Critério | Descrição |
| --- | --- |
| CA1 | Todo push em `main`/`develop` e todo pull request rodam a verificação sem ação manual. |
| CA2 | Uma etapa rápida (sem Docker) dá retorno em poucos minutos, e a etapa completa só roda se ela passar. |
| CA3 | O resultado fica disponível para a revisão: o status no PR e, como artefato, o relatório e os logs dos serviços, inclusive quando falha. |

## Workflow

`.github/workflows/verificacao.yml`:

| Job | Quando | Passos |
| --- | --- | --- |
| `estatica` | push em `main`/`develop`, pull request, manual | Node 24, `npm ci`, `npm run verificar -- --rapido --sem-relatorio` (timeout de 15 min) |
| `completa` | depois de `estatica` passar | `npm ci`, `npm run verificar -- --manter`, logs dos serviços, artefato `verificacao-<n>` (relatório e `servicos.log`, 14 dias), `down -v` (timeout de 45 min) |

- `concurrency` cancela execuções antigas da mesma branch. `permissions: contents: read`.
- Os passos de log, artefato e limpeza rodam com `if: always()`, ou seja, também quando a verificação falha.
- O runner `ubuntu-latest` já traz Docker e Compose v2. O `package-lock.json` inclui os binários nativos de Linux
  (`@esbuild/linux-x64`, `@rolldown/binding-linux-x64-gnu`), e o mesmo `npm ci` já roda nas imagens Docker.
- Não há segredos: a verificação usa `.env.example` e `CANAL_ENVIO=log`.

## Evidência e pendências

- O YAML foi validado localmente (estrutura, gatilhos, dependência entre jobs e passos).
- Os comandos que o workflow executa foram executados nesta máquina e aprovados (veja [US-20](US-20.md)).
- **Pendente: nenhuma execução no GitHub.** As branches desta implementação não foram enviadas (combinado com a
  equipe). A primeira execução real acontece no primeiro push ou PR que contiver `.github/workflows/verificacao.yml`.
  Até lá, CA1 e CA3 ficam sem evidência. Depois da primeira execução, registre aqui o link e a duração.
- Recomendação para o PO e o Scrum Master: exigir o job `estatica` como verificação obrigatória da branch `develop`
  nas regras de proteção do GitHub. Isso só pode ser configurado por quem administra o repositório.
- **Pendente:** revisão por outra pessoa (pela tabela de revisores, Sofia Avallone revisa a US-21).
