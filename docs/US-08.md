# US-08 — Reutilizar paciente cadastrado ao agendar

Rastreabilidade **R01 e R07**. Dependências **US-02 e US-04**. Base `develop` em `3ef80b6`, que inclui a US-07.

## Fluxo e contratos

1. A Recepção envia `POST /api/cadastro/pacientes/busca-cpf` pelo gateway com o CPF no corpo
   JSON. O Cadastro aceita onze dígitos ou a máscara padrão, consulta a chave única e retorna
   HTTP 200 com `{ paciente: { id, cpf, nome, telefone } }` ou `{ paciente: null }`.
   CPF inválido retorna 400. Falha no Cadastro ou em seu banco é distinta de CPF ausente.
2. Se encontrado, o formulário preenche nome e telefone com os dados do mestre. Alterar o CPF
   invalida os dados e a busca anterior. Para CPF novo, os campos ficam disponíveis para edição.
   Se o Cadastro estiver indisponível, a recepção pode tentar novamente ou escolher continuar
   com dados manuais. O CPF não é colocado na URL dessa busca.
3. `POST /api/agendamento/consultas` aceita `idPaciente` (UUID opcional) e preserva os campos
   existentes. A consulta e a outbox são gravadas na mesma transação. A resposta contém
   `idPaciente` (corresponde à coluna `id_paciente`) e `vinculoPacientePendente: true`.
   O ID vindo da busca é imediato e fica sujeito à confirmação pelo Cadastro. Sem ID, a consulta
   começa com `idPaciente: null`.
4. O Cadastro já consome `consulta.agendada` v1 e, em uma transação, deduplica, resolve o mestre
   por CPF e publica via outbox `paciente.atualizado` v1 com a correlação `consulta-<id>`.
   Um CPF existente conserva os dados do mestre. Consultas concorrentes convergem para o mesmo ID.
5. O Agendamento assina `paciente.atualizado` v1 na fila durável `agendamento.pacientes`. O consumidor
   valida o envelope e usa a correlação e o CPF para confirmar apenas a consulta correspondente.
   A deduplicação por `id_evento` e a confirmação ocorrem na mesma transação local. O Agendamento
   grava o ID canônico e baixa a pendência, que desaparece da agenda no próximo polling. Eventos
   de edição de contato têm correlação `paciente-<id>` e não alteram o vínculo.

O fluxo usa as seções 4, 5 e 7 da proposta de arquitetura. A Recepção consulta o Cadastro pelo gateway,
e os serviços trocam eventos pelo RabbitMQ usando seus próprios bancos. Os contratos de eventos v1
continuam compatíveis com a Notificação. Mensagens inválidas ou que esgotam três tentativas seguem
para a exchange de erros existente. Os logs novos omitem dados pessoais e o conteúdo dos eventos.

A migração preserva as consultas anteriores com `idPaciente: null` e sem indicação de pendência.
O reprocessamento histórico fica para uma operação separada.

## Como verificar

Use um projeto Compose local isolado e `CANAL_ENVIO=log`. O teste para e reinicia apenas o serviço
`cadastro` do projeto de teste, cujo nome padrão é `iesi-clinicadigital-us08-teste`. Os registros criados são fictícios.

```sh
npm run typecheck
npm test
npm run build
docker compose -p iesi-clinicadigital-us08-teste up -d --build --wait
npm run test:us08
```

Para usar outro projeto, configure `COMPOSE_PROJECT_NAME`. Se usar um override de portas, configure `COMPOSE_FILE`, `TEST_BASE_URL` (gateway) e
`TEST_RABBITMQ_URL` para o mesmo projeto. O roteiro automatizado cobre busca exata, consultas
concorrentes para CPF novo, reutilização de ID mestre, correção de ID provisório, reenvio do evento
e vínculo após a retomada do Cadastro.

Para demonstrar os critérios pela interface, abra **Nova consulta** nos três cenários.

| Critério | Evidência em 09/11/2026 (America/Fortaleza) | Implementação |
| --- | --- | --- |
| CA1 | O navegador preencheu nome e telefone a partir do mestre e salvou sem redigitação. A integração conferiu o ID imediato e confirmado, além da correção de um ID provisório divergente. | `e5292fc`, `244f16e`, `1d2639e` |
| CA2 | O navegador reconheceu CPF novo por Enter, habilitou os campos e salvou a consulta. Na integração, duas consultas concorrentes receberam o mesmo ID e o Cadastro retornou um único mestre. | `e5292fc`, `244f16e`, `1d2639e` |
| CA3 | Com `cadastro` parado, o navegador exibiu indisponibilidade e ofereceu nova tentativa ou entrada manual. O agendamento manual mostrou vínculo pendente. A integração confirmou o ID após a retomada do serviço. | `4cc0a1f`, `244f16e`, `1d2639e` |

Na mesma data, passaram o typecheck e o build dos workspaces, os quatro testes unitários,
o build e a subida do Compose isolado com PostgreSQL/RabbitMQ, os dois cenários de
`npm run test:us08` e os três cenários da regressão da US-07 em `npm run test:integracao`.
O gateway de teste usou a porta local 28080 e o RabbitMQ a 25672.
