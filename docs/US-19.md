## Como reproduzir

Pré-requisitos: Docker em execução (Engine 25 ou mais nova, por causa do `start_interval` dos healthchecks) e Node 24.
`npm install` não é necessário para o roteiro: ele só usa o Node para os scripts.

```powershell
npm run ambiente:limpo                 # roteiro completo em projeto isolado; remove tudo ao final
npm run ambiente:limpo -- --sem-cache  # idem, reconstruindo as imagens sem cache e baixando as bases de novo
npm run ambiente:limpo -- --manter     # deixa o ambiente no ar em http://localhost:18080
```

O roteiro usa o projeto Compose `iesi-clinicadigital-us19-limpo`, a configuração de exemplo (`--env-file .env.example`)
e portas próprias: recepção 18080, serviços 13001 a 13003, RabbitMQ 25672 e 25673, bancos 15433 a 15435. Por isso
ele não encosta no projeto padrão da equipe nem em testes de outras histórias que estejam no ar. Também não lê o `.env`
local, que pode ter credenciais do WhatsApp. Ele se recusa a rodar com o nome do projeto padrão, porque apaga os volumes
do projeto que usa. Para trocar o nome ou as portas, use `US19_PROJETO` e `US19_<VARIAVEL>_PORTA`, por exemplo `US19_RECEPCAO_PORTA`.

| Passo | Comando executado pelo roteiro | Verificação |
| --- | --- | --- |
| Preparação | `docker compose -p <projeto> --env-file .env.example down --volumes --remove-orphans` | nenhum volume do projeto |
| Execução 1 | `... up -d --build --wait --wait-timeout 300` | 8 containers `healthy`; `_prisma_migrations` com todas as migrações de cada serviço; `/api/<serviço>/saude` e a tela respondem pela recepção; logs com `Applying migration` |

| Execução 2 | `... down` (sem `-v`) e o mesmo `up` | 8 `healthy`; logs com `No pending migrations to apply` nos três serviços; contagens idênticas |
| Carga de novo | `node scripts/popular-demo.mjs` | "nada foi gravado" e contagens idênticas |
| Registro | `docker compose images`, `docker image inspect`, `psql`, `rabbitmqctl`, `node -v`, `prisma -v`, `nginx -v` | versões e digests |

A saída fica em [evidencias/us19-ambiente-limpo.txt](evidencias/us19-ambiente-limpo.txt), já sanitizada: caminho do
repositório, nome do computador e usuário do sistema são trocados por marcadores. Padrões de e-mail, CPF e telefone
são mascarados. Só entram no arquivo as linhas de migração dos logs dos serviços, nunca o log inteiro.

Para subir o ambiente padrão da equipe, sem isolamento, o caminho continua o do README:

```powershell
Copy-Item .env.example .env
docker compose up --build --wait
npm run demo:popular
```

## O que mudou

**Compose e Dockerfiles (US-19-T1).** O Cadastro (US-01) já estava no Compose, com banco próprio, migrações no início e
dependências de saúde. A revisão encontrou três lacunas, todas corrigidas:

| Lacuna | Efeito | Correção |
| --- | --- | --- |
| Serviços e recepção sem healthcheck | `up --wait` liberava assim que o container iniciava, antes das migrações e da API | healthcheck `wget /saude` nos três serviços (`start_period` 60 s para as migrações) e na recepção; a recepção depende dos três `service_healthy` |
| Portas fixas no host | um segundo ambiente (limpo ou de teste) exigia arquivo de override | `${RECEPCAO_PORTA:-8080}` e equivalentes; o padrão não muda; lista comentada no `.env.example` |
| Recepção sem `restart` | se o nginx caísse, ficava fora até subir à mão | `restart: unless-stopped`, como os serviços |

O `Dockerfile` do Cadastro ganhou o comentário de contexto de build que os outros já tinham. Nenhum serviço, evento ou
contrato HTTP mudou.

Hipótese descartada: suspeitei que `sh -c "npx prisma migrate deploy && node ..."` não repassasse o SIGTERM ao Node.
Medido no `node:24-alpine`, o `docker stop` leva cerca de 1,2 s e sai com código 0, igual à versão com `exec`, porque o
`sh` do busybox já executa o último comando no lugar do shell. Não houve alteração.

**Carga de dados fictícios (CA2).** `scripts/popular-demo.mjs` agora lê os dados de `scripts/dados-demo.mjs`:

- CPF `000.000.NNN-DV` com o último dígito verificador trocado. Nenhum CPF válido é igual a eles, e o teste confere de 1 a 999.
- Telefone `81 9 0000-0NNN`, faixa não atribuída a linhas móveis. Antes, os números tinham formato de linhas reais
  (`81 98812-…`) e poderiam receber WhatsApp com `CANAL_ENVIO=whatsapp`.
- Nomes com o sobrenome "Exemplo"; profissionais também.

O roteiro espera a recepção e os três serviços responderem. Em banco vazio, agenda 6 consultas (5 pacientes, um com duas
consultas). Depois espera o lembrete da última e a cancela. Em seguida confere a propagação por eventos: vínculo de
paciente confirmado em todas as consultas, um lembrete por consulta, lembrete da cancelada em `cancelado`, e os 5
pacientes no Cadastro. Com a agenda já populada, não grava nada e só confere. A saída tem só contagens e estados, e
termina com os endereços de onde obter as evidências.

## Erros encontrados durante a execução

- A primeira versão da evidência marcava "alterações locais não commitadas" só por causa do próprio arquivo de evidência.
  O roteiro passou a ignorar esse arquivo nessa checagem.

## Limites

- O roteiro não testa a ausência de imagens base no cache local. `--sem-cache` reconstrói as camadas do projeto e
  revalida as tags com `--pull`, mas não apaga imagens já baixadas.
- A carga cria consultas para hoje às 08:30, 10:00 e 14:30. Com a antecedência padrão de 24 h, os lembretes de consultas
  em menos de 24 h saem logo pelo canal `log`. Por isso a contagem por estado (`enviado`/`programado`) varia com o horário
  da execução. Os totais não variam.
