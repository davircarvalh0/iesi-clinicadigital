# US-17: Retornar erros previsíveis para entradas inválidas

Rastreabilidade R07 e R15. Entradas inválidas recebem 400 com uma mensagem que diz o que corrigir, antes de qualquer
gravação. Nada é criado na tabela de consultas nem na outbox.

## Regras de validação

| Campo | Regra | Mensagem |
| --- | --- | --- |
| CPF | 11 dígitos, com ou sem máscara (`000.000.000-00`). Só o formato: o dígito verificador não é conferido (decisão do grupo). Letras e tamanhos diferentes são recusados. | `CPF inválido. Use 11 dígitos ou 000.000.000-00.` |
| Telefone | DDD sem zero à esquerda e número de 8 ou 9 dígitos, com código do país `55` opcional. É a mesma regra do Cadastro. Máscara é aceita. | `Telefone inválido. Informe DDD e número.` |
| Início (`inicio`) | ISO 8601 com fuso. Datas inexistentes (por exemplo, 30/02) são recusadas. | `Data e hora inválidas. Use o formato ISO 8601 com fuso.` |
| Nome | Ao menos 3 caracteres. | `Nome deve ter ao menos 3 caracteres.` |

Antes, o Agendamento removia qualquer caractere que não fosse dígito do CPF e só conferia o tamanho, então `abc12345678901` era aceito.
Telefones zerados (`00000000000`) também passavam.

## Formato da resposta

- Validação: `400 { "erro": "Dados inválidos. <motivos>", "detalhes": [...] }`. Os motivos são mensagens fixas, sem eco do valor enviado.
- JSON malformado: `400 { "erro": "JSON inválido" }`. Antes respondia 500 no Agendamento e na Notificação (o Cadastro já tratava).
- Corpo grande demais: `413 { "erro": "Dados da requisição excedem o limite." }`.
- Consulta inexistente: `404 { "erro": "Consulta não encontrada" }`. Consulta já cancelada: `409 { "erro": "Consulta já cancelada" }`. Não mudaram.

## Parâmetro `limite`

`GET /eventos` (Agendamento) e `GET /atividades` (Notificação):

| Entrada | Resultado |
| --- | --- |
| Ausente | 30 |
| Inteiro de 1 a 100 | Esse valor |
| Inteiro acima de 100 | Reduzido a 100 (comportamento anterior) |
| Zero, negativo, decimal ou não numérico | `400 { "erro": "Dados inválidos. Limite inválido. Informe um inteiro a partir de 1." }` |

Antes, `limite=-5` chegava ao banco como `take: -5`, que inverte a leitura, e valores não numéricos viravam 30 sem aviso.
A paginação do Cadastro (`pagina` e `tamanhoPagina`) já rejeitava valores abaixo de 1 e não foi alterada.

## Exemplos fictícios

```http
POST /api/agendamento/consultas
{ "nome": "Paciente Fictício", "cpf": "abc12345678901", "telefone": "81900000017",
  "profissional": "Profissional Fictício", "especialidade": "Teste", "inicio": "2026-12-01T10:00:00-03:00" }

400 { "erro": "Dados inválidos. CPF inválido. Use 11 dígitos ou 000.000.000-00.", "detalhes": [...] }
```

```http
GET /api/agendamento/eventos?limite=-5

400 { "erro": "Dados inválidos. Limite inválido. Informe um inteiro a partir de 1." }
```

## Critérios e evidência

| Critério | Evidência reproduzível |
| --- | --- |
| CA1 | Unitário (`services/agendamento/test/us17.test.ts`): CPF fora do formato, telefone inválido, data inexistente e JSON malformado respondem 400 com a mensagem. Integração: as mesmas entradas pelo gateway não alteram a lista de consultas nem as linhas da outbox. |
| CA2 | Integração: consulta inexistente devolve 404 e consulta já cancelada devolve 409, para cancelar e para remarcar, sem gerar eventos. |
| CA3 | Unitário e integração: `limite` negativo, zero, decimal ou não numérico devolve 400 nas duas rotas; `limite` alto é reduzido a 100. |

## Limites conhecidos

- O dígito verificador do CPF não é validado, por decisão do grupo. CPFs com formato correto e dígitos inválidos continuam aceitos.
- Datas passadas continuam aceitas no agendamento: a política de consulta passada ainda depende de decisão do grupo.
