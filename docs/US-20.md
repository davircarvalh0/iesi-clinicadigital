# US-20 · Verificação reproduzível em um comando

Épico E6 (Qualidade e entrega). Branch: `feat/us-20-verificacao`, criada sobre `feat/us-15-envio-real-controlado`.

> **Critérios inferidos.** O catálogo `03_user_stories.md` não estava disponível. No Product Backlog, o E6 é "execução
> reproduzível e verificação": a US-19 cobre a execução reproduzível, e a US-21 é a "automação ampliada", primeiro
> corte em caso de falta de capacidade. Por isso a US-20 foi interpretada como a verificação de todas as camadas de
> teste com evidência. Confirme com o PO.

Antes desta história, cada suíte tinha seu próprio roteiro de execução (Compose de teste, banco isolado, variáveis
`TEST_*`), espalhado por 19 documentos. Uma suíte que ninguém rodava podia quebrar sem ser notada. Isso aconteceu: as
suítes US-11, US-14 e US-16 estavam quebradas no `develop` depois das mesclagens (veja a seção sobre a integração).

## Critérios (hipótese)

| Critério | Descrição |
| --- | --- |
| CA1 | Um único comando roda typecheck, build, testes unitários, testes de banco e roteiros de integração em um ambiente isolado criado do zero, sem interferir no ambiente da equipe. |
| CA2 | O comando grava a evidência: data, commit, versões e, por etapa, o comando, o resultado, a contagem de testes e a duração. Termina com código diferente de zero se algo falhar. |
| CA3 | Existe um modo rápido sem Docker, para usar antes de cada commit, e uma rastreabilidade de cada história até os testes e o comando que a verificam. |

## Uso

```bash
npm run verificar -- --rapido   # etapa estática, sem Docker
npm run verificar               # tudo; remove o ambiente isolado ao final
npm run verificar -- --manter   # tudo; deixa o ambiente em http://localhost:38080
```

| Etapa | O que roda |
| --- | --- |
| 1. Estática | `npm run typecheck`, `npm run build`, `npm test` (unitários de todos os workspaces, sem banco), `npm run test:scripts` |
| 2. Ambiente | `docker compose -p iesi-clinicadigital-verificacao --env-file .env.example up -d --build --wait`, depois de `down -v`. Portas 3xxxx (configuráveis por `VERIFICAR_<PORTA>`), `CANAL_ENVIO=log`, `OPERACAO_HABILITADA=true`. |
| 3. Banco | Cria `notificacao_teste` e `cadastro_teste` nos Postgres do ambiente, separados dos bancos dos serviços, porque os testes ligam a própria rotina de envio. Aplica as migrações e roda a suíte da Notificação e `test:us01:db`, `test:us02:api` e `test:us14:db` do Cadastro. |
| 4. Integração | `demo:popular` na agenda vazia, cada `scripts/usNN.integracao.test.mjs` (um por vez, em ordem) e `us01.reinicio`. |
| 5. Limpeza | `down -v --remove-orphans` (exceto com `--manter`) |

O relatório fica em [`docs/evidencias/verificacao.md`](evidencias/verificacao.md), com o caminho do repositório e o
nome da máquina mascarados. Uma etapa que falha não interrompe as seguintes; se o ambiente não sobe, as etapas de
banco e integração aparecem como puladas. A contagem lê os blocos `ℹ tests/pass/fail/skipped` do `node --test`
(`scripts/contar-testes.mjs`, com teste próprio).

A rastreabilidade de cada história até os testes e o comando que a verificam está em [rastreabilidade.md](rastreabilidade.md) (US-23).

## Integração das branches pendentes

Para que a verificação rodasse sobre o produto inteiro, as branches prontas e ainda fora do `develop` foram mescladas
em `integracao/us06-us11-us17`. A US-06 tinha sido mesclada no `main` (PR #16), não no `develop`. A primeira execução
completa encontrou defeitos deixados por mesclagens anteriores no `develop`:

| Defeito | Efeito | Correção |
| --- | --- | --- |
| A rotina de envio perdeu a verificação de autorização da US-14 na mesclagem `3a59ba8` | **Lembretes saíam sem autorização de contato** | Verificação restaurada antes de cada tentativa e teste `us14-rotina.test.ts` |
| `ItemConsulta.tsx` não compilava (resolução de conflito incompleta) | `npm run typecheck` e o build da recepção falhavam | Componente reconstruído com US-10/11/12/14/18 |
| `StatusLembrete` da recepção sem `bloqueado` | Tipo divergente da API | Restaurado |
| Pendência de sincronização tratava só `enviado` como encerrado | Cancelar uma consulta já lembrada deixava "Sincronização pendente" para sempre | `simulado`, `aceito_provedor` (e depois `incerto`) também encerram |
| A carga fictícia da US-19 não registrava autorização | Com a US-14 de volta, todos os lembretes da demonstração ficariam bloqueados | Autoriza todos os pacientes menos um, sem criar versões ao rodar de novo |
| US-14 e US-16 (integração) esperavam o status `enviado` | Os roteiros falhavam depois da US-12 | Esperam `simulado` ou `aceito_provedor` |
| Canais falsos dos testes US-10/11 sem `canalContato`; testes de banco rodando em paralelo no mesmo banco | O teste US-11 travava; resultados intermitentes | Canais corrigidos e suíte da Notificação sequencial |

## Evidência em 24/11/2026

Execução completa (`npm run verificar`) sobre a branch da US-15 com estes arquivos: **aprovada**. Foram 30 etapas,
com 251 de 255 testes aprovados. Os 4 pulados são os testes de banco na etapa estática, que rodam com banco na etapa 3.
O ambiente subiu do zero em 125 s. Modo rápido: 4 etapas, 138 de 142 testes.

## Limites

- Os testes de integração criam dados fictícios e não os apagam. Por isso a verificação recria o ambiente a cada execução.
- O tempo total é de cerca de 6 minutos, dominado pelo build das imagens.
- A US-10 e a US-12 têm testes de unidade e de banco, mas não têm roteiro de integração próprio. O fluxo delas é
  exercitado pelas integrações da US-13, US-14 e US-16.
- **Pendente:** revisão por outra pessoa (pela tabela de revisores, Sofia Avallone revisa a US-20).
